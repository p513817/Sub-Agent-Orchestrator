AOrchestra · The contributionWhat it buys — before how it works

Stop hiring a fixed cast. Write the role at runtime.

The gap
Every prior system ships a fixed cast of roles, decided before the task is seen.
A task outside the cast has nobody to do it.
The move
A role becomes a fillable work order: ⟨I, C, T, M⟩ — written fresh per subtask, executed, discarded.
And that work order can itself be learned.
What it bought
+22.13
average pass@1 — 71.62 vs 49.49 — over three benchmarks, same backbone.
And it costs about 11×.
The paper’s own words: an agent is “a quadruple ⟨Instruction, Context, Tools, Model⟩” — a recipe for composing capabilities on demand.

An agent
Φ = ⟨ I, C, T, M ⟩
An agent is not a model — it is a model plus what it was told, what it knows, and what it may touch. Swap any one field and you have a different worker.

AOrchestra · Formalisation 2/2One round, formally · and what the whole run is for

Those two lines were the vocabulary. These two are the loop.

That arrow,
formally
st+1 = δ( st, at, ot )
  • Elsewhere δ just appends the observation.
  • Here ot is already a reviewer’s summary, and the orchestrator rewrites it again. Two lossy compressions before anything enters the state.
What all the
rounds are for
maxπ 𝔼 [ 𝟙{ Success(G) } − λ · Cost(τ) ]
  • Not a training loss — the system’s purpose. Get it right, minus λ times what it cost.
  • The paper never gives λ a value, so in the headline runs it is effectively 0. That is why they cost 11×.
AOrchestra · Learning 1/2§3.3 · Two ways to make an orchestrator better

Change the weights, or change the words

Both act on the orchestrator alone. SFT learns to compose (I, C, T); ICL learns to route M.

B runs 5 rounds of 6 trajectories, with Claude Sonnet 4.5 doing the rewriting — so it is not self-reflection; it hires an outside coach. A’s training data is on p22.
AOrchestra · Learning 2/2§3.3 · the two updates, formally

One is a gradient. The other is a rewrite.

Same two columns as the previous slide — left is still A, right is still B.

A · the weights
θ★ = arg maxθ Σt log pθ(a★t | st)
Pick the weights that make the teacher’s move most probable at every state.
Ordinary supervised fine-tuning. The only unusual part is the label — a whole work order, not a word.
B · the words
Imaink+1 = OPTIMIZE(Imaink, τk, Perf, Cost)
Imain is the orchestrator’s own strategy block — not the I inside Φ, which is what it writes for a sub-agent. Rewriting the manager’s handbook, not the work orders.
OPTIMIZE is not an operator: it is an LLM call — the prompt is printed in Appendix B.3.1.
Nothing in B is differentiable. A paragraph of English has no derivative — so only A is training, and that is not a matter of convention.
AOrchestra · LearningTable 5 · what it was actually trained on
  • The table shows the knobs, not the data. The seed set is TaskCraft — a task generator, not a benchmark: ~36K synthetic tasks, difficulty-scalable, multi-tool, verifiable.
  • The teacher runs on it and every quadruple it writes is recorded — 2,000 trajectories, no human labels.
  • So training is synthetic and evaluation is GAIA · Terminal-Bench · SWE-Bench. The zero-shot claim rests on that separation.
One knob matters: max length 16K. At 16K a bloated context would not fit the training data at all.
AOrchestra · SetupTable 6 · Tools and hard limits
Each benchmark hands sub-agents a different toolset — and the timeouts are brutal: 10 s for code, 30 s for search, 300 s for SWE-Bench tests. These numbers bound how much any single step can achieve.

III

ParaManager

Teaching the conductor to dispatch several at once

ParaManager · The contributionWhat it buys — before how it works

Stop dispatching one at a time. And stop being the biggest model in the room.

The gap
Tools and agents speak different interfaces, and the orchestrator fires one call per turn.
Independent subtasks queue for no reason.
The move
One interface for both, then train a 4B model to fire up to 4 at once.
SFT for the format, RL for the judgement.
What it bought
56.44 → 70.48
the same Qwen3-4B — +14.04, while directing models far larger.
Trained on maths alone. Does not win the two code benchmarks.
The weight of the title falls on the second half: “Unified Agent-Tool Orchestration with Parallel Subtask Decomposition.” “Small model” is the result, not the motivation.
ParaManager · Solution 1Agent-as-Tool
“abstracts both agents and tools into a
standardized, learnable action space through
protocol normalization and explicit state feedback.”
ParaManager · Abstract

Tk(p) = (v, σ)　　σ ∈ {OK, PARSE_ERR, EXEC_ERR, TIMEOUT}

One form, one receipt — and a malformed call returns a status light instead of crashing, so the next turn can repair it.

ParaManager · FormalisationState, action, termination
Unified call
o ≜ Tk( p ) = ( v, σ ), σ ∈ { OK, PARSE_ERR, EXEC_ERR, TIMEOUT }
One signature for tools and agents. A broken output becomes a signal, not a crash.
State
st = ( q, ℋt, bt ), ℋt = { ( ri, ai, oi ) }i=1..t−1
Question, history — and remaining budget. Budget is inside the state, so the policy can price its own moves.
Action
at = { ( kt,j, pt,j ) }j=1..nt, 1 ≤ nt ≤ nmax = 4
A set, not a single call. This one line is the whole paper.
Executor
ot,j = Tk( p ) if νt,j = 1, else ( ∅, PARSE_ERR )
Each call is validated independently. One bad call in a parallel batch doesn’t sink the other three.
Termination
ẑ ∼ Ms( · | q, ℋT, rT, cend )
The 4B never writes the answer — a frozen summariser does. Deciding and writing are separate jobs.
ParaManager · Solution 2Figure 1 · Parallel dispatch
  • One turn, up to four concurrent calls.
  • Three tiers — 7 tools (2 basic + 5 agent) + 3 backbone models, all hard-coded. final_answer is a separate terminate action, not one of the 7.
  • search is a local Wikipedia retriever, not web search.
ParaManager · Solution 2Figure 10 · The orchestrator’s prompt
You are a routing and synthesis engine. All sub tasks must be delegated. — and Do not blindly trust tool responses; always validate critical results. That second line is what the case studies act out.
ParaManager · TrainingFigure 2 · SFT then RL
SFT keeps recoverable error trajectories — runs that hit EXEC_ERR or TIMEOUT and repaired themselves — rather than only ever showing a clean first-try success. Where the data comes from, and what the loss actually optimises — next two pages.
ParaManager · Training§4.2 · Where the data comes from

One well, two buckets — kept strictly apart.

SFT Data
  • Runs the framework itself (Qwen3-30B-A3B-Instruct-2507) on DAPO-Math — not hand-labeled.
  • Sample eight, keep at most one — prioritise the run that recovers from a tool failure.
  • A tool-balance constraint stops one tool from dominating the retained set.

→ 4,470 instances

RL Data
  • Same DAPO-Math pool — no separate source.
  • Sample eight outputs per question with the same model.
  • Discard all-correct / all-incorrect questions — zero variance, zero signal.

→ 3,742 instances

Any question already used for RL is removed before building the SFT set. Stated leakage control, not an accident of how the split fell.
ParaManager · TrainingEq. 9 · What the mask actually buys
Loss
ℒSFT(θ) = −𝔼τ Σℓ mℓ log πθ( yℓ | y<ℓ )
Ordinary next-token negative log-likelihood — with one twist: the mask mℓ.
The mask
mℓ = 1 iff token ∈ rt or at, else 0
1 on ParaManager’s own reasoning and action tokens. 0 on every environment-side token.
One round, linearised — which tokens the loss actually sees Case study 1 · full exchange at p51
rt reasoning
counted — “…the code_reasoner output says the sum is 55… but we must verify the binary representation and the logic using independent tools.”
at action
counted — {"name":"code_reasoner",…} {"name":"critical_reviewer",…}
ot observation
masked out — critical_reviewer replies: “…every assumption is justified… the final answer 55 is indeed correct.” Whatever the tool says back, mℓ = 0.
Two rows train the policy. The third only ever conditions it.
Focuses SFT on the generation rules of orchestration policies rather than fitting environment-side tool outputs. Not maths — format, call-count, when to stop. And the same mask resurfaces in RL’s importance ratio (Eq. 20) — not an SFT-only trick.
ParaManager · TrainingThe reward — four terms, plainly summed

R(τ) = Rtask + Rfmt + Rdiv + Reff

TermChecksWhat it prevents
Rtask = 𝕀[ ẑ = GT(q) ]Is the final answer right?— the base objective, binary
Rfmt = 1T Σt Fmt(yt)Valid <reasoning> / <tool_call> each turn?Malformed output that can’t execute at all
Rdiv = ½( Rpar + Rtool )
Rpar = 𝕀[ (1/T)Σt nt ≥ θpar ]   Rtool = 𝕀[ |U(τ)| ≥ θtool ]
 Really parallelising, and using more than one kind of tool?Path collapse — settling on one safe tool forever
Reff = ½( Rlen + Rcost )
Rlen, Rcost = 1 if x ≤ target, else max(0, (2·target−x)/target)
 Tokens and tool spend inside budget?Rambling and tool-spamming with nothing to show

Efficiency uses a soft budget — full marks under target, linear decay past it, zero past double. A hard cliff would scare the model off tools entirely.

Advantage

  • GRPO is DeepSeek’s (DeepSeekMath, 2024) — no critic, the group mean is the baseline.
  • The exponent mℓ is ParaManager’s addition: 1 on its own tokens, 0 on tool output. Grade the student, not the exam paper.
